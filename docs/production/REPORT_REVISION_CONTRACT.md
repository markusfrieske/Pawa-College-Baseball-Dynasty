## Required accepted-result invariants

1. **Revision identity.** A report has stable league/game/report identity. Every content revision is append-only and identifies its predecessor, normalized observed data, completeness, author, reason, creation time, rules/roster contract versions and evidence manifest. An edit counter is a concurrency token, not a substitute for retained historical content.
2. **Reviewed identity.** A confirm, dispute or commissioner resolution names the exact revision the actor saw. Refetching must not silently replace that identity underneath a retained draft or review. The server checks current authority and legal state again inside its transaction. Unknown or stale versions fail without writes; the client preserves work and asks the actor to compare the newer content.
3. **One official receipt.** Each game has one active accepted-result identity. Its receipt references the accepted immutable revision (or seeded simulation result), approving actor and authority, finalization algorithm/version, time and durable effect identity. A retry for the same operation returns that same receipt; a different requested result conflicts. Historical receipts and supersession remain inspectable.
4. **Atomic required effects.** Approval/state, receipt, official game, standings, player lines, pitcher workload/rest, coach record/XP and required audit either commit together or remain unchanged. Durable staged effects require an explicit resumable state that cannot masquerade as complete. No correctness-critical effect can exist only in an in-memory batch accumulator.
5. **Defined ordering.** All competing writers take the game lock before the report lock. They re-read state under those locks. Report creation, approval, dispute, direct-score finalization, simulations and correction use one compatible protocol. Multi-game projection locking must also have a deterministic team/player order to avoid cross-game deadlocks; game-level locking alone does not establish league chronology.
6. **Baseball reconciliation.** Corrections validate complete normalized content before acceptance. Runs, inning lines, team totals, actual roster identities and player counters agree under the declared supported rules. Unknown statistics remain unknown, with no fabricated player lines. Rule-specific inning/tie/mercy/workload choices remain in the [pending inputs](POWER_PROS_CONTRACT_INPUTS.md), not inferred from current restrictions.
7. **Traceable amendments.** Correcting an accepted result creates an authorized superseding revision and reason. Either reverse/reapply explicit per-game contributions or rebuild dependent projections deterministically; do not add the new totals on top of the old. Preserve original evidence, approvals and receipts. Rest chronology and downstream games must be reconciled or explicitly block the amendment.
8. **Evidence and recovery.** Accepted manifests retain source hashes/identifiers, extraction version and correction identity. Pending OCR jobs cannot mutate accepted evidence. A consistent backup restores revisions, receipts, required effects and evidence relationships as one state. Missing legacy evidence remains explicitly unknown rather than fabricated.
9. **External effects.** Inbox/news/recap work is distinct from official acceptance. If reliable delivery is promised, persist an outbox event keyed by receipt within the acceptance transaction and deliver idempotently after commit. Best-effort notifications are not proof of durable delivery or player receipt.

## W03 batch 01 bounded acceptance

The first slice must reject absent, malformed and stale PATCH versions; allow one of two simultaneous edits at the same base version; increment once; reject edits after a completed game or finalization sentinel even if report status is stale; and commit the edit plus required edit audit together. Existing populated reports must gain a valid initial version without changing their baseball data. The client must capture the version with the loaded edit draft and retain it through background refetches and failed submissions.

Independent synthetic HTTP/PostgreSQL checks must inspect persisted report and audit rows, use real authenticated roles and inject an audit failure to prove rollback. A pure draft/version check is useful but cannot certify browser navigation, reload recovery or visual usability. This slice keeps TI-05 implementing until confirm/dispute/finalize and immutable acceptance satisfy the broader contract.

## W03 batch 02 bounded acceptance

[W03 batch 02](W03_BATCH_02.md) implements reviewed-state guards for confirmation, dispute and commissioner resolution, atomic decision/audit with core finalization, and atomic PATCH correction provenance. The existing field name `editVersion` now advances for disputes and acceptance as well as body edits; it is a current-state concurrency token. Deterministic queued race tests cover both orders of edit/confirm, dispute/confirm, edit/finalize and duplicate confirmations. CPU acceptance failure leaves pending state. Secondary feed failures do not return a failed decision after its transaction committed.

A repeated accepted request currently returns conflict, not an identity-bearing idempotent receipt. The game sentinel has no immutable content reference, and initial submission/evidence/role/roster boundaries are not fully transactional. These limits keep TI-05 implementing.
