# Class of Nine game-dev working instructions

For Class of Nine interface work, first read [PC game UI guide](docs/art-direction/pc-sports/GAMEDEV_GUIDE.md), the relevant screen's authored brief in `docs/art-direction/pc-sports/research/`, and the latest production evidence. Frisk explicitly changed the target to **PC-only**; old mobile-first layout requirements are historical and superseded. Do not optimize the game for phone or touch play.

Preserve the approved Class of Nine gateway/wordmark and forest/brass Varsity Club identity. Design each screen around its particular decision, selected subject and sport context; a common frame does not justify repeating a dashboard layout. Reference screenshots establish visual evidence, not hands-on usability or permission to copy protected art or gameplay rules.

The PC atlas is a design proposal with fictional data, not shipped gameplay. Keep proposed controls, implemented behavior, tested behavior and enjoyment evidence separate. Never expose undisclosed scouting values, turn unknown stats into zero, or present a pending report as official to improve a mockup.

Scheduled development remains paused. Work only from Frisk's manual instructions. Maintain one writer on the development branch, preserve unrelated changes and saves, and verify meaningful changes before reporting completion. Do not infer deployment or main-branch merge approval from a design decision.
